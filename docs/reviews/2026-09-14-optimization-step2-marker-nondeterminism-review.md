## 2. 取证

### 2.1 实测 1：线上复现（探针，3 次请求）

```bash
uv run python tools/probe_concept_and_optimization.py --out <产物>.json
```

发出的第二步提问（逐字，落在 `opt-step2_question`）：

```text
【优化第二步】只做「以性能为先」方向的优化，具体要求：用哈希表把嵌套循环降为 O(n)。不要顺带做其他方向的改动（例如：「以可读性为先」：拆分长方法并命名中间变量）。请给出优化后的完整代码。
```

**提问确实带标记**（同一串还作为 `user_question` 回显在痕迹的 `retrieval.query` 里），而回答是：

```text
…请选择你要优化的方向。
【编辑建议】
{"kind":"options","target":"Solution.java","options":[{"goal":"performance",…},{"goal":"readability",…}]}
```

⇒ 与用户描述逐字吻合（第二张同样的方案卡、一行代码都没有）。诊断字段落下
`verdict="discriminator-ineffective"`（工具新增，见 §3.3）。

### 2.2 实测 2：不是「未重发」（指纹 + git）

- 同一条痕迹里含 `critic_issues` / `revise_outcome` / `revise_revert_reason` 三键——它们由**同批次**的
  评审优化计划 Task 6 加进 `build_final`（`nodes.py:829-832`）。
- `git log -S`：三键与 `STEP2_MARKER`、`render_intent_guidance` **落在同一个提交** `12e3f4b`
  （`fix: 1. 评审-修订优化 2. 修复代码优化bug`），且 `HEAD == @{u} == 12e3f4b`（已推送）。

⇒ 已部署构建**包含**新的优化引导段（本地导出确认：`_main_system_prompt()` 第 76-93 行就是标记判别器条款）。
本条排除「先重发再验」这一类解释。

### 2.3 实测 3：同一提问的重复率（8 次请求）

对**同一字面提问**、两种 payload 形状各 4 次（形状差异与判据无关，见下）：

| 形状 | payload 差异 | replace | options |
|---|---|---|---|
| `A_min` | 探针原形状（无 `run_mode`、无显式 `intent`） | 4 | 0 |
| `U_ui` | 真实前端形状（带 `run_mode=default`、`test_case_count=0`） | 4 | 0 |

连同实测 1 与 §2.4 的 2 次 ablation，**同一提问共 10 次：1 次 `options`、9 次 `replace`**。

8 次 `replace` 的块形态逐条核验过：`goal="performance"`、`target="Solution.java"`、
`code` 393–456 字符、不含 `...` 占位、无 `options` 字段 ⇒ **成功时交付形态是对的**，失效方式是「偶发回落成方案卡」。

> ⚠ 诚实标注：n=9（同一提问）只能给出量级（≈1/10），不能给可信区间；真实前端提问的选项文案与我的 fixture 不同，
> 率可能不同。但「**非确定性**」这一性质不依赖样本量：同一字面提问在两次独立观测里给出了不同的 `kind`。

### 2.4 实测 4：意图 ablation（2 次请求）——顺手排掉一个嫌疑

第二步提问被分类成 `data_query`（痕迹 `intent` 字段）。同一提问**显式指定** `intent`：

| 显式 intent | 结果 |
|---|---|
| `data_query`（与分类结果同值，作对照） | `replace` |
| `other` | `replace` |

⇒ 意图**不足以单独触发**该失效（但见 §3.2：它仍是错的，且是本批新引入的耦合）。

## 3. 判定与建议

### 3.1 根因：只有祈使句，没有门闩（与评审链路同源）

要求「带标记 ⇒ 必须 replace」目前只落在两处**模型可违背**的地方：

1. 系统提示的条款（`prompting/optimization.py`，注入 `_main_system_prompt()`）；
2. 一条 few-shot（本地导出第 182-185 行）——其提问文本与本例**几乎逐字相同**，正确答法是 `replace`。

实证：模型仍然偶发不遵守。**因此把交付判据交给模型自证是不可靠的**——这与本批次给评审链路下的结论是同一个：
「修订必须可回滚」之所以成立，是因为它把判据做成了**代码**（相似度/块保全/引用不劣化），而不是提示词。
优化第二步缺的正是同一件东西。

**建议（需先改 spec/plan 再执行）**——复用 harness 既有 propose→guard 回路（与 `verification` 校验同层），加**确定性门闩**：

- **判据（纯字符串/JSON，不看模型）**：当 `user_question` 以 `【优化第二步】` 起头（或提问带「上一版优化代码没有通过…」的返修形状）时，
  候选终答必须**恰好一个**【编辑建议】块，且 `kind == "replace"`、`code` 非空、不含 `...` 占位、无 `options` 字段。
- **不过怎么办**：拒绝该终答，回灌一条错误观察（如「第二步必须交付 `replace` 完整代码，你给的是 `options`；
  不要再让用户选方向」）让模型重提案，受既有 `MAX_ROUNDS` 约束；轮次用尽则按现有收束策略交付并记痕，
  痕迹里加一个 `optimize_step2_gate` 字段（passed/violated），使「有没有兜住」可度量。
- **不做**：不改前端标记、不改协议、不改两步式的产品形态（判别器仍然只有标记一个，只是改由代码判定）。

### 3.2 附带发现：`intent` 被误判成 `data_query`，且本批把它变成了「行为性」输入

- 分类器 `conservative_intent` 的 `DATA_QUERY_KEYWORDS` 含「变量」；第二步提问的排除项文案
  （本例「拆分长方法并命名中间变量」；线上真实产出的「添加注释并改进变量命名」）**必命中** ⇒ `intent=data_query`。
  D7 只把「第」做了形状化，同类漏判换了个词继续存在。
- **本批新引入的耦合**：Task 3（D4）把 `build_context_node` 从硬编码 `"other"` 改成
  `build_system_prompt(intent)`，于是 `intent` 从「只进痕迹」变成**真的会注入角色与输出契约**。
  `CONTRACTS["data_query"]` 写的是「必须回答：在哪一步、哪一行、哪个变量…长度 3-6 句」——
  与「交付整份 `replace` 代码」直接竞争。
- **判定**：不是本次失效的触发条件（§2.4 已证），但**它是错的**，且这条耦合是这批改动新开的。
  修法二选一（建议后者）：① 给「变量/值/数组」也加形状约束；② 把标记前置到关键词之前——
  凡提问以 `【优化第二步】` 起头，`intent` 直接不取 `data_query`。

### 3.3 工具缺陷（本次已修）

`tools/probe_concept_and_optimization.py` 的 docstring 自称「与前端 `buildGoalPrompt` 同构」，
**实际漏了标记** ⇒ 任何人用它复跑都会永远看到 `options`，进而**误判为「修复完全无效」**。
这是同一字面量的**第三个副本**（coze / 前端 / 探针各一份），而只有前两份有握手断言。

已改（本仓 `tools/` 内，未动业务代码）：

| 改动 | 说明 |
|---|---|
| 从 coze 源 `import STEP2_MARKER` | 消灭第三副本；探针提问与前端模板已实测**逐字相同** |
| `diagnosis` 落盘 | 按「第二步块 kind」×「痕迹批次三键」给三类判定：`not-redeployed` / `discriminator-ineffective` / `coze-side-ok`；避免复跑时各说各话 |
| `options_source` 标注 | 明确第二步用的是 `step1` 的真实选项还是 `fixture`（本次实测 1 落在 fixture，原因见下条） |
| `parse_options` 改平衡解析 | 原按 `"\n\n"` 切分的写法遇到「options 块后紧跟【视角导航】块」**必然解析失败**并**静默**回落 fixture |

## 4. 验收口径修正

- 本件计划 §3 的端到端判据是「opt-step2 返回 `replace` 而非 `options`」——**单次通过不足以判过**，
  因为它对偶发失效没有分辨力（本次 10 次里 1 次失败就是证明）。
  改为：**同一提问连测 N=10 全部 `replace`**，且**门闩的失败回灌用例**（FakeModel 故意产 `options`）在离线绿。
- `AGENT.md` 状态表里「评审-修订子系统优化 **spec**」行的状态写成了「已执行」，
  spec 应为「已定稿」（同类 spec 行都这么写）——本次已顺手订正为「已定稿」。
- 联调侧可零成本自查前端这一腿：用户消息气泡显示的就是**发出的原文**
  （`player.js` 的 `chatMessages.push({role:'user', text:q})`），点完方向后看那条提问是否以
  `【优化第二步】` 起头即可。若不以标记起头 ⇒ 前端未重新构建部署，属另一条独立问题。

## 5. 局限（必须与结论分开说）

1. **样本小**：同一提问 9 次，只能判「非确定性」这一性质，不能给可信的失效概率。
2. **提问文案是探针构造的**（用 fixture 选项按前端模板拼），与用户原话不同；用户原话在截图之外不可得。
3. **只验了 coze 侧**：浏览器侧是否真的发出标记无法从这里验证（§4 给了自查办法）。
4. **未改业务代码**：本次只交付审查结论与取证工具修正；门闩属设计变更，须先更新 spec 再更新 plan。
